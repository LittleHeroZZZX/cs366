这个字符的`__repr__`方法返回字符串"'\\x00'"，而使用 `print` 方法打印时不显示任何内容。

> (c) What happens when this character occurs in text?

它的行为与直接调用该字符的`__repr__`方法或者打印该字符的方法一致，即当调用`__repr__`时会以十六进制的字符串的形式展示，打印时就好像不存在这个字符。

It behaves the same as when you directly call the character's __repr__ method or print it: calling __repr__ displays it as a hexadecimal
string, while printing it makes it appear as if the character doesn't exist.

## Problem (unicode2): Unicode Encodings (3 points)

> (a) What are some reasons to prefer training our tokenizer on UTF-8 encoded bytes, rather than UTF-16 or UTF-32?
> It may be helpful to compare the output of these encodings for various input strings.

随着编码标准的增加，生成的字节流的长度显著变长，这意味最终生成的序列长度更长。而 Transformer 架构的计算复杂度与序列长度成平方关系，
因此更长的序列会显著增加计算成本。

With the increase in encoding standards, the generated byte stream becomes significantly longer, which means the final sequence length
is also greater. Since the computational complexity of the Transformer architecture is quadratic with respect to the sequence length,
longer sequences lead to a significant increase in computational cost.

> (b) Consider the following (incorrect) function, which is intended to decode a UTF-8 byte string into
> a Unicode string. Why is this function incorrect? Provide an example of an input byte string
> that yields incorrect results.
> def decode_utf8_bytes_to_str_wrong(bytestring: bytes):
> return "".join([bytes([b]).decode("utf-8") for b in bytestring])

"今天吃了吗？"，这个字符串无法被正确解码。因为原函数错误地将每个字节都单独解码，而 UTF-8 编码中有些字符是由多个字节组成的，
因此对于多字节编码的字符，将无法正确解码。

The string "今天吃了吗？" cannot be decoded correctly. This is because the original function incorrectly decodes each
byte individually, but in UTF-8 encoding, some characters are composed of multiple bytes. Therefore, characters with
multi-byte encodings will not be decoded correctly.

> (c) Give a two byte sequence that does not decode to any Unicode character(s).

[0xFF, 0xFF] 这个字节序列无法解码为任何 Unicode 字符，因为这是一个无效的起始字节。

The byte sequence [0xFF, 0xFF] can't be decoded to any Unicode character, as it is an invalid leading byte.
